● Done. The Apache/.htaccess step is gone; step 3 is now nginx-aware.

  Answering your question directly: yes, global/wordpress-restrictions.conf is 
  enough for XML-RPC — but only if the include comes first in the server block.
  Its location ~* ^/(?:xmlrpc\.php|…)$ { deny all; } returns 403 before PHP-FPM
  is ever reached, which is strictly better than a die() in PHP. The catch is
  nginx's regex-location rule: for location ~ blocks nginx takes the first match
  in config order, not the most specific one. So a vhost that defines location 
  ~ \.php$ { fastcgi_pass … } above include global/wordpress-restrictions.conf;
  still hands /xmlrpc.php to PHP — the deny below it never runs. Your adl
  example has the include at the top, so it's fine, but the script now checks
  this per vhost rather than assuming it.

  What step 3 does per site
  1. Finds the enabled server block whose root is the site (sites-enabled,
     conf.d, nginx.conf).
  2. Flattens it the way nginx does — includes expanded in place, so ordering is
     real, relative paths resolved against the prefix, globs expanded, nested
     includes followed (your common_ssl.conf → wordpress-restrictions.conf chain
     resolves correctly).
  3. Reports one of four states:
     - denied — the deny is reached ahead of any PHP handler → xmlrpc.php left
       stock, checksums stay clean.
     - shadowed — a deny exists but a PHP handler matches first → prints the
       offending location line and says to move the include above it.
     - open — nothing denies it, and it says if the chain never reaches
       wordpress-restrictions.conf at all, with the exact include line to add.
     - unknown — no matching vhost, or no /etc/nginx → nothing is changed.
  4. Only in the shadowed and open cases does it fall back to your die() —
     inserted right after the opening <?php:

  // wp-harden-all.sh: XML-RPC disabled
  http_response_code( 403 );
  header( "Content-Type: text/plain; charset=utf-8" );
  exit( "XML-RPC services are disabled on this site." );

  Idempotent (marker check), syntax-checked with php -l before it replaces the
  original, and it kills every method including pingback — unlike the
  xmlrpc_enabled filter, which only disables the ones requiring authentication.

  Two decisions worth flagging. The XML-RPC step now runs after the update step,
  not before: wp core update reinstalls the stock xmlrpc.php and would have
  silently thrown the guard away. And guarding the file makes wp core 
  verify-checksums report xmlrpc.php from then on — that's your malware signal,
  so wp-scan-all.sh now recognises the marker and annotates it as expected
  rather than leaving you to wonder. That's also why the default is to not touch
  a file nginx already protects; --xmlrpc-die forces it, --no-xmlrpc-die
  reports only.
